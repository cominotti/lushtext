# flathub-publication Specification

## Purpose
Define LushText's release automation, version metadata synchronization, validation gates, and Flathub publication handoff requirements.

## Requirements

### Requirement: Domain-Based Flathub Verification
The release documentation and verification tooling SHALL guide maintainers through verifying `dev.cominotti.lushtext` as a custom-domain Flathub app ID using the `cominotti.dev` domain.

#### Scenario: Verification target is derived from the app ID
- **WHEN** a maintainer asks how to verify `dev.cominotti.lushtext` on Flathub
- **THEN** the documented verification target is `https://cominotti.dev/.well-known/org.flathub.VerifiedApps.txt`
- **AND** the documentation states that the token is generated by Flathub after the app is available for verification

#### Scenario: GitHub account linking is not treated as custom-domain verification
- **WHEN** the maintainer's GitHub account is linked with Flathub
- **THEN** the workflow MUST NOT claim that this verifies the `dev.cominotti.lushtext` app ID
- **AND** it explains that GitHub-hosting verification applies only to supported hosting-site app ID prefixes, not this custom-domain ID

#### Scenario: Local verification detects HTTPS problems
- **WHEN** the maintainer runs the domain verification check
- **THEN** it fails if `https://cominotti.dev` cannot be reached with a certificate valid for `cominotti.dev`
- **AND** it reports the failing verification URL before the maintainer asks Flathub to verify it

#### Scenario: Local verification detects token publication
- **WHEN** the maintainer runs the domain verification check with an expected Flathub token
- **THEN** it fetches `https://cominotti.dev/.well-known/org.flathub.VerifiedApps.txt`
- **AND** it succeeds only when the token appears as a non-comment line in that file

### Requirement: Intelligent Release Commands
The project SHALL provide Makefile release commands that can either release an explicit semver tag or compute the next semver tag from existing Git tags.

#### Scenario: Explicit release validates the requested version
- **WHEN** a maintainer runs `make release VERSION=v1.2.3`
- **THEN** the release helper validates that the version matches `vMAJOR.MINOR.PATCH` with an optional prerelease suffix
- **AND** it refuses to continue if the tag already exists

#### Scenario: Bump release computes the next stable version
- **WHEN** a maintainer runs `make release-bump TYPE=minor`
- **THEN** the release helper finds the latest stable `v*` tag
- **AND** it computes the next version by incrementing the requested major, minor, or patch component

#### Scenario: Prerelease stream increments safely
- **WHEN** a maintainer runs `make release-bump TYPE=minor PRERELEASE=alpha`
- **THEN** the release helper starts or continues the matching `vMAJOR.MINOR.PATCH-alpha.N` stream
- **AND** the numeric suffix is greater than any existing matching prerelease tag

#### Scenario: Stable promotion requires confirmation
- **WHEN** prerelease tags exist for the computed stable version
- **THEN** the release helper refuses to create the stable tag unless promotion is explicitly requested

#### Scenario: Release can be previewed without mutation
- **WHEN** a maintainer runs a release command with `DRY_RUN=1`
- **THEN** the helper reports the computed version, intended file changes, validation plan, commit message, tag, and push targets
- **AND** it does not modify files, create commits, create tags, or push

### Requirement: Release Metadata Stays Synchronized
The release workflow SHALL keep all LushText package and store metadata versions synchronized before creating a release tag.

#### Scenario: Version surfaces are updated together
- **WHEN** the release helper prepares version `v1.2.3`
- **THEN** `meson.build`, `crates/lushtext/Cargo.toml`, `crates/lushtext-core/Cargo.toml`, `Cargo.lock`, and `data/dev.cominotti.lushtext.metainfo.xml.in` reflect release version `1.2.3`

#### Scenario: AppStream release notes are required
- **WHEN** the release helper prepares a real release
- **THEN** it refuses to create a release commit or tag unless release notes are provided through a deterministic release-notes input
- **AND** the AppStream release entry includes the release version, current release date, and release description

#### Scenario: Version mismatch blocks tagging
- **WHEN** any package, Meson, Cargo lock, or AppStream version surface does not match the requested release version after preparation
- **THEN** the release helper fails before creating a commit or tag

### Requirement: Release Validation Gates
The release workflow SHALL fail closed before publishing a tag when local release prerequisites or packaging checks are not satisfied.

#### Scenario: Release starts from clean main
- **WHEN** a maintainer runs a real release command
- **THEN** the helper verifies that the current branch is `main`
- **AND** the working tree is clean before release metadata is generated

#### Scenario: Release stages only intended generated files
- **WHEN** the helper creates a release commit
- **THEN** it stages only the intended release metadata and packaging files
- **AND** it fails if any unrelated tracked or untracked file would be included

#### Scenario: Metadata validators pass
- **WHEN** a real release is prepared
- **THEN** AppStream metadata validation and generated desktop-entry validation pass before the tag is created

#### Scenario: Cargo sources are current for Flatpak
- **WHEN** a real release is prepared
- **THEN** `build-aux/cargo-sources.json` is regenerated or verified against `Cargo.lock`
- **AND** stale vendored sources block tag creation

#### Scenario: Flatpak release build is validated
- **WHEN** a real release is prepared locally or by the release workflow
- **THEN** the Flatpak manifest builds successfully from the release inputs before the release is considered publishable

### Requirement: Flathub Manifest Update Pull Request
The release automation SHALL prepare a reviewable update for the Flathub manifest repository that references the immutable public GitHub release source.

#### Scenario: Flathub manifest does not use a local checkout source
- **WHEN** a Flathub-facing manifest is generated for version `v1.2.3`
- **THEN** its application source references the public GitHub release tag, archive, or commit for `v1.2.3`
- **AND** it does not use the local-only `type: "dir"` checkout source

#### Scenario: Flathub manifest preserves packaging invariants
- **WHEN** the Flathub-facing manifest is generated
- **THEN** its app ID, command, runtime, SDK, Rust SDK extension, Meson release profile, finish arguments, and Cargo vendored sources match the reviewed LushText Flatpak packaging contract

#### Scenario: Release workflow opens a Flathub PR when configured
- **WHEN** a release tag workflow completes release validation and Flathub credentials are configured
- **THEN** it opens or updates a pull request against the Flathub manifest repository for `dev.cominotti.lushtext`
- **AND** the pull request includes the release tag, source commit, validation summary, and manual test instructions

#### Scenario: Missing Flathub credentials are reported honestly
- **WHEN** the release workflow lacks the token or repository configuration needed to open a Flathub pull request
- **THEN** the workflow reports that the Flathub PR step was skipped or failed due to missing configuration
- **AND** it does not claim that Flathub publication is complete

#### Scenario: Flathub automerge is not the default
- **WHEN** the Flathub update path is configured
- **THEN** it keeps human review and testing as the default publication gate
- **AND** it MUST NOT enable Flathub bot automerge unless a maintainer explicitly opts into that policy in a later change

### Requirement: Release CI Covers The Flathub Path
GitHub Actions SHALL exercise the release-specific Flatpak and Flathub update path before maintainers depend on it for a real release.

#### Scenario: Release dry run runs in CI
- **WHEN** a pull request changes release scripts, Flatpak manifests, AppStream metadata, desktop metadata, or cargo vendoring
- **THEN** CI runs a release dry-run or equivalent check that validates version computation and release packaging checks without publishing a tag

#### Scenario: Tag workflow validates release artifacts
- **WHEN** a `v*` tag is pushed
- **THEN** the release workflow checks out that tag
- **AND** it validates AppStream metadata, desktop metadata, Cargo vendored sources, and the Flatpak build for the tagged source

#### Scenario: Release workflow creates GitHub release context
- **WHEN** the tag workflow succeeds
- **THEN** it creates or updates the GitHub Release context needed by downstream release assets and Flathub update messaging
- **AND** it keeps benchmark-report upload behavior compatible with the existing release benchmark workflow
