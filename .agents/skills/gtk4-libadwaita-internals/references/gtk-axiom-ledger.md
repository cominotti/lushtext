# GTK Axiom Ledger

## Contents

- [Rules](#rules)
- [The ledger](#the-ledger)
- [Envelope use](#envelope-use)

The normative list of GTK, `GtkListBase`, `GtkScrollable`, and Adwaita
behaviours that LushText and GTK Lush geometry designs (and, from A21, window
lifecycle designs; from A22, tree-model expansion designs; from A23, the
text-layout, text-buffer, input-method, accessibility and GtkSourceView
behaviours the long-line designs depend on; from A37, text-view frame-phase
behaviours; from A38, the GIO GSettings keyfile-backend behaviours window
construction and the settings writer depend on; from A42, the paragraph,
edit-signal and widget-lifecycle behaviours of the document scale policy;
from A59, the input, input-method, drag-and-drop, key-binding and hidden-text
behaviours Protected View's interaction model depends on, several driven with
real input through the private compositor's RemoteDesktop interface)
depend on. Most
geometry bugs in 2026 came from a wrong belief about one of these, not from code missing
its own spec (see `docs/next/formal-verification.md` §1), so each belief is
written down here once, with a stable id, the designs that rely on it, and how
it is pinned against real GTK.

## Rules


- **A design that starts relying on a GTK behaviour not listed here adds an
  entry in the same change.** Ids are stable and never reused.
- **Every axiom is pinned by an isolated headless probe** in the GTK Lush
  family crate `gtk-lush-axioms` (`crates/gtk-lush/axioms/`: a minimal
  pure-GTK fixture, no LushText or GTK Lush widget), or its row records why it
  cannot be pinned. Each probe has one runnable sample,
  `crates/gtk-lush/axioms/examples/<name>.rs`, that builds the same fixture:
  interactive by default for a person to watch
  (`make gtk-axiom-sample AXIOM=<id>`), and a headless verdict with `--check`
  (`CHECK=1`). `make gtk-axioms` runs every probe and every sample's `--check`
  under a private `mutter --headless`, never the live desktop; the probe
  runner is the `axiom_probes` test of `gtk-lush-adoption-lab`. "Indirectly"
  means a consumer test would fail if the axiom broke, but no probe isolates
  it. LushText's consumer tests stay beside every probe: the probe says what
  GTK does, the consumer test says LushText, under its own CSS and
  application, stays inside those conditions.
- **The ledger, the catalogue, the probes and the samples agree.**
  `make check-gtk-axioms` (in `make check-policy`) fails when an id is in one
  and not the other, a probed entry lacks its sample or names a probe for
  another id (the build already rejects a missing probe function), a sample
  names an unknown axiom, a row claims a probe the catalogue lacks (or
  omits one it has), or a "Pinned by" cell names the retired LushText-hosted
  probes. Adding an axiom: see the crate README.
- **Verdicts are structural; durations are recorded values.** A probe decides
  its verdict only from positions, geometry, tag membership, signal and call
  counts, captured log messages and buffer state, never from a duration, so a
  slow runner cannot flip it. A fixture that reaches its state only after a
  toolkit time limit (A29's 2000 ms cut-off) grows until it does, up to a cap,
  and reaching the cap is `FixtureInvalid`, never `Violated`. A probe that
  provokes a toolkit `CRITICAL` on purpose (A29, A32) captures it with the
  crate's `LogCapture`, which restores the previous log handling.
- **Slow probes.** A probe whose fixture must run for seconds is marked
  `slow` in the catalogue only if the pull-request `GTK Axioms` job would
  otherwise approach its `timeout-minutes` (never raise the timeout instead).
  The pull-request job (`GTK_LUSH_AXIOMS_INCLUDE_SLOW=0`) then prints
  `skipped (slow): <id>`, local `make gtk-axioms` and the nightly
  responsiveness workflow run it, and its row's "Pinned by" says `**slow**`
  and that it runs nightly (`make check-gtk-axioms` enforces both). No probe
  is slow today: A29, the longest, takes about 8 s in isolation.
- **A probe that fails after a toolkit update is an axiom change**, reviewed as
  such: revisit the entry, every dependent design, and every verification
  envelope that cites the id before the failure is resolved. Do not adjust the
  probe to match the new behaviour first.
- **Verification envelopes derive from this ledger.** A model that treats GTK
  as nondeterministic (the Kani slice-bin loop model in
  `crates/gtk-lush/widgets/src/kani_proofs.rs`) restricts GTK only with
  `kani::assume` clauses that cite an id below; an envelope narrower than the
  pinned statement is recorded as an explicit assumption in the model and in
  the programme record.

## The ledger

"Verified against" is copied from the `gtk`/`adw` fields of the observation
lines `make gtk-axioms` prints, never assumed, and names where it ran, because
the host and the CI container can carry different micro versions. The GNOME 50
platform floor is GTK 4.22 / Libadwaita 1.9 / GtkSourceView 5.20 (the Snap and
source builds); the shipped runtime is GNOME 51, GTK 4.24 / Libadwaita 1.10 /
GtkSourceView 5.22 (the Cominotti Flatpak, the Fedora 45 toolbox and CI).
**Version-qualified axioms.** Where a toolkit release changed a verdict, the
row states each verdict with its bound (`GTK < 4.24` / `GTK ≥ 4.24`), the
catalogue entry names the bound (`version_bound`), and the probe asserts the
verdict of the toolkit it runs on and prints the branch it asserted
(`asserted_branch`); either side still fails on any further change.
`make check-gtk-axioms` requires both ranges in such a row. "Verified against"
then lists a run on each side: the shipped runtime (Fedora 45) and the floor
(`make gtk-axioms-runtimes` against `org.gnome.Sdk//50`, or the Fedora 44
`GTK Axioms (GNOME 50 floor)` job).

## Envelope use

The Kani closed-loop model of the slice bin
(`crates/gtk-lush/widgets/src/kani_proofs.rs`, `slice_loop`) cites these ids in
its `kani::assume` clauses: A4 for where a request appears, A5/A6 for why the
band is never a zero page, A7 for the child's anchor (a host publish or
write-back re-anchors it at any row of the content; a request anchors it at the
target row inside the view; the value is re-derived from that anchor on every
allocation), A8 for how far the child's own estimate correction may move it,
A9 for why an emitting publish rules out a request in that allocation and why
landing must be exact, A11 for outer clamping, and A13 for why the outer move
happens after the allocation.

The A7/A8 settle envelope was an **assumption** bounded by the child's own
correction until `extend-closed-loop-geometry-verification`: the A7 probe had
measured 4.42 px of value per pixel of page change after a host move, and the
adoption lab then reproduced it through the bin (a 4664 px jump on maximize).
The model now carries the child's anchor explicitly instead: a host-published
(stray) anchor re-derives the value anywhere on another page, which is what GTK
does, and an anchor inside the view is narrowed to keep it; the bin's fix
(`classify_child_scroll_in_frame`) was model-checked against it first.

The breakpoint-loop Kani model
(`crates/lushtext-core/src/ui/window/geometry/kani_proofs.rs`) models Adwaita
as an envelope built from A14–A18, and each `kani::assume` in its Adwaita step
cites the id it rests on. A14 backs how a condition is evaluated: `max-width:
N sp` matches exactly when the allocated width in px is at most `N × text
scale`, inclusive, which equals the policy's px-against-whole-sp comparison
only at text scale 1.0. A15 backs when a threshold re-tuned by
`sync_properties_breakpoint` takes effect: not inside `set_condition`, but at
the allocation it schedules in the next frame, so a changed condition is
evaluated one step after the step that set it. A16 backs setter timing and
restore: setters change after the bin has allocated its child for that frame,
the child sees them one frame later, and an unapply restores the value from
`add_setter` time, overwriting what `sync_secondary_surfaces` wrote while the
breakpoint was applied. A17 backs the widths the policy's sp shares become and
the rule that toggling `show-sidebar` or `collapsed` never changes the window
width, so the loop's only width input is the window's own allocation. A18
backs the width domain (the window's minimum is its `width-request`, 640 px,
once breakpoints exist) and the single-current-breakpoint rule: only the
last-added matching breakpoint applies, so below the Open-button condition
(400 sp) neither the workspace `collapsed` setter nor the properties
`layout-name` setter is applied. Any assumption narrower than these statements
is recorded in the model and in `docs/next/formal-verification.md`.
